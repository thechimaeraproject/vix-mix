# Kit CLI adoption

**Adopted 2026-11-04, with the bootstrap ([handoff 00](handoffs/00-bootstrap.md)), at the kit's
release tag `kit-source.json` pins.** Vix Mix declares itself to the kit's `kit` command through
`kit.repo.json` at the repository root. The kit's
[CLI reference](https://github.com/thechimaeraproject/chimaeraproject-kit/blob/master/handbook/reference/kit-cli.md)
defines the manifest fields and the commands, and
[Adopt the kit CLI](https://github.com/thechimaeraproject/chimaeraproject-kit/blob/master/handbook/cookbook/adopt-the-kit-cli.md)
is the procedure followed; this record says what Vix Mix declares, what stays here, and what
changed observably. Vix's [kit-cli.md](https://github.com/thechimaeraproject/Vix/blob/master/docs/kit-cli.md)
is the shape it follows: a Rust workspace with Node only for the kit.

The everyday loop — branch, `kit push`, green checks, `kit merge`, and what each refusal
means — is the kit's cookbook
[Work on a change](https://github.com/thechimaeraproject/chimaeraproject-kit/blob/master/handbook/cookbook/work-on-a-change.md),
condensed into the `kit-work-on-a-change` skill under `.claude/skills/` and `.agents/skills/`.

## What Vix Mix takes

- **The manifest.** `kit.repo.json` names the repository (`vix-mix`,
  `thechimaeraproject/vix-mix`, default branch `master`, role `consumer`), its one push gate
  (`check`), that it installs the tooling from the root (`kit.npm: ["."]`), its Cargo side
  (`kit.cargo: { manifests: ["Cargo.toml"], lock: "Cargo.lock" }`), that it releases nothing
  (`release.kind: none`, no release gates), the workflow that produces its two required checks
  (`ci.yml`; `check (linux)` and `check (windows)`), the workflow `kit merge` dispatches on
  `master` after every merge (`ci.onMerge: ["linux-build.yml"]`: the Linux release tarball,
  kept as the run's artifact), that nothing deploys, and that only a repository admin merges
  (`protect.merges: admins`).
- **`dev` is the kit's Node runner over a registry of cargo commands.** `dev.run` is
  `{node} scripts/dev.mjs` and `dev.registry` is `scripts/dev/tasks.mjs`: `check` needs `fmt`
  (`cargo fmt --all --check`), `clippy` (`cargo clippy --workspace --all-targets -- -D
  warnings`), `test` (`cargo test --workspace`) and `check-docs` (the tooling's
  `kit-check-docs`, run as `{node} node_modules/@chimaeraproject/tooling/bin/kit-check-docs.mjs
  --root .`), in that order. The cargo commands' exe is the `{cargo}` token. The root
  `package.json` has one dependency, `@chimaeraproject/tooling`, from `npm.rhyes.org` through
  `.npmrc`; it is also the tooling pin `kit bump` moves.
- **The documentation standard.** `kit.docs.config.mjs` declares `docs`, the code roots
  `crates/*` and `app`, and three reasoned exemptions (tests, fixtures, build output); the six
  references partition the roots, and `dev check-docs` holds it on every push and in CI.
- **The Cargo pin.** The four kit crates are git dependencies on one tag under
  `[workspace.dependencies]`; `Cargo.lock` resolves each at that tag's commit, and
  `kit-source.json` records the commit. The first adoption was by hand (the kit's issue #188:
  `kit bump` cannot make the first one); `kit bump` moves all three from now on.
- **The hooks and the Claude Code guard.** `.githooks/` and the `PreToolUse` entry in
  `.claude/settings.json` are generated by `kit hooks install` and committed; `pre-commit` runs
  the doctor rows a staged manifest can break, `pre-push` refuses a push that did not come
  through `kit push`, and the guard refuses `git push`, `git tag`, `npm publish`,
  `gh pr merge` and `gh workflow run` from an agent.
- **The skills.** `kit-work-on-a-change`, `kit-docs-standard` and `kit-report-an-issue` under
  `.claude/skills/` and `.agents/skills/`, generated by `kit skills install` and committed.
- **The CI trigger.** `.github/workflows/ci.yml` runs on `pull_request` (opened, synchronize,
  reopened) and `workflow_dispatch` only. Its one job is a matrix whose check-run names are
  exactly `check (linux)` and `check (windows)`, which `ci.required` lists and the ruleset will
  require. It fetches the private kit with the `KIT_TOKEN` secret through a step-scoped
  `insteadOf` and `CARGO_NET_GIT_FETCH_WITH_CLI`, as Vix's does.
- **The ruleset**, once the bootstrap PR has merged: `kit protect --apply` derives it from the
  manifest — `master` takes only a PR with both checks green, rebase-merged by a repository
  admin; no force-push, no deletion.

## What stays in Vix Mix

- The toolchain pin (`rust-toolchain.toml`), the cargo gates themselves, and `.cargo/config.toml`
  (`git-fetch-with-cli`, so Cargo reads the private kit with this machine's credentials).
- The Linux leg's PipeWire setup in `ci.yml`: the packages, and
  `scripts/ci/headless-pipewire.sh`, a headless PipeWire and WirePlumber with a null sink and a
  null source, proven to answer before the gates run.
- The Linux leg runs on `ubuntu-latest`, not on the organisation's self-hosted runner the kit's
  cookbook (step 6) names: it installs system packages and runs a PipeWire daemon of its own,
  which a fresh hosted VM gives for free and an ephemeral shared runner may not.

## What changed observably

- `dev` with no arguments prints the registry; `dev check` runs the four gates in order.
- `git push` from this checkout is refused by `pre-push`; a branch reaches origin through
  `kit push --yes`, which runs `dev check` first.
- `kit doctor` checks the manifest, the shims, the hooks, the skills, the Cargo pin
  (`cargo.tag-agrees`, `cargo.one-source`), the npm registry and the docs standard.

## How you know it worked

`kit doctor`, `kit hooks check` and `kit skills check` are green but for the rows that need the
remote PR flow (`ci.required-known` until the first `kit push`, `protect.ruleset` until
`kit protect --apply`); `dev check` exits 0; `git push origin master` is refused with "pushes go
through `kit push`"; the bootstrap PR's `check (linux)` and `check (windows)` are green and
`kit merge` merged it.
