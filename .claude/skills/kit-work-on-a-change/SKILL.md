# Work on a change

Every change reaches the default branch as a PR, through `kit push` and `kit merge`. Hooks, the
Claude Code guard and the GitHub ruleset refuse every other channel.

## Before you act

- Run `git status` and `git branch --show-current` first. Never commit on the default branch
  (`master` in the kit and Nexus, `main` in rhyes) or on a detached HEAD.
- Changes you did not make are normal: other sessions work in parallel. Mention them once, never
  revert them, and stage by name (`git add <file>…`), never `git add -A` or `git commit -a`.
- On an idle checkout, run `kit doctor --offline`, then the fix each failing row prints.
- A pull, rebase or switch that prints `dependencies changed (…) — run kit sync` moved a lockfile
  or the kit pin: run `kit sync` before anything else.
- A kit bug, or a mistake of yours a clearer kit doc would have prevented: file it now with the
  `kit-report-an-issue` skill, then continue.

## Start a branch

```bash
git fetch origin
git switch -c fix/<what> origin/<default>                # works whoever holds the default branch
git worktree add -b fix/<what> <dir> origin/<default>    # or: the branch in a worktree of its own
```

A new worktree has nothing installed — no `node_modules`, no `.venv`. Run `kit sync` in it before
any gate, `kit doctor` or `kit push`; until then `kit push` refuses (`dev.runner-resolves`) or its
gates fail.

## Change and commit

- In the kit, a change a consumer could notice adds a bullet under `## Unreleased` in
  `CHANGELOG.md` on the same branch; `kit release` refuses an empty section.
- Change a doc and the code it describes in the same commit.
- Write the message to a file and run `git commit -F <file>`. The guard matches the text of a
  Bash command, so an inline message that mentions a refused command can block the commit.
- The pre-commit hook runs the doctor rows the staged paths affect; its refusal names the fix.
- A visual change to a design package is not done when the design tier passes; it sees each widget
  alone. `kit link` it into the consumer it is for and look there (desktop and mobile widths, light
  and dark) before the release: *Check a design change in the consumer*, under Long form.

## Before `kit push`: fetch and compare

```bash
git fetch origin
git rev-list --left-right --count origin/<default>...HEAD   # prints: behind ahead
git rev-list --left-right --count origin/<branch>...HEAD    # once the branch is pushed
```

- Behind `origin/<default>`: `git rebase origin/<default>`. Rebase, never merge: history is
  linear, and a PR carrying a merge commit cannot be rebase-merged. (`kit merge` does this
  rebase itself.)
- `origin/<branch>` has commits you lack: `git pull --rebase origin <branch>`.

## Push

`kit push --yes` in the branch's checkout, or `kit push <branch> --yes` from any worktree; never
`git push`: refusals, offline doctor, push gates, a one-time intent, the PR, and dispatch of the
workflows GitHub does not run itself. Uncommitted tracked changes are set aside while the gates
run and put back after (`not part of this push: …`), so never stash by hand around it — the
stash is shared by every worktree. Watch with `kit status` or `gh pr checks`; Linux legs queue
on one self-hosted runner, so waiting is not failing. Its ahead and unpushed counts are ancestry,
not delivery: after a rebase, cherry-pick or integration branch, run
`git cherry origin/<default> <branch>` and `git range-diff` to see what is already there before
you push, merge or delete — and a review worktree's uncommitted files are in no commit, so
patch equivalence alone never clears its removal.

## When it refuses

Read the message and run the fix it names. Never retry the same command unchanged.

| Refusal | Fix |
|---|---|
| a gate failed (exit *n*, nothing pushed) | `dev <gate-id>` reproduces it; fix, commit, push again |
| no worktree has the named branch checked out | the `git worktree add "<dir>" <branch>` it prints |
| tracked files still differ after being set aside | `git add --renormalize .`, commit it, push again |
| behind `origin/<default>`, or merge commits beyond it | `git rebase origin/<default>` (it flattens merges; integrate lanes by rebase or cherry-pick), then `kit push --yes` |
| origin's copy of the branch has commits you lack | `git pull --rebase origin <branch>` |
| no commits beyond `origin/<default>` | commit the change first |
| hooks generated by a newer tooling than installed | `kit sync` |
| hooks missing or stale | `kit hooks install`, then commit `.githooks/` |
| `core.hooksPath` is not `.githooks` and resetting it failed | the fix it names, then `kit hooks install` (push, merge and sync reset it themselves otherwise) |
| `skills.fresh` fails | the fix it prints: `kit skills install` and commit the skill directories, or `kit sync` when the installed tooling is behind |
| an npm root is linked | `kit unlink` — before the kit worktree it points into is merged, too. Consumer work needing an unreleased kit: versioning.md § Co-developing with `kit link` |
| on the default branch, or HEAD detached | start a branch as above |
| `kit doctor --offline` fails | the fix it prints beside each row; in a new worktree, `kit sync` |

## Merge

`kit merge <branch> --yes` (or the PR number) from the main checkout; plain `kit merge --yes` in
the branch's own checkout; never `gh pr merge`. Without `--yes` it asks once, and a session with
no terminal gets exit 2. On the default branch with nothing named it lists what there is to merge.

- It pushes first whatever the branch's worktree has and the PR lacks, then **waits** for the
  checks — the default — until GitHub shows that head. A waiting merge outlasts the Bash tool's
  ten-minute limit: run it in the background, or with `--no-wait` once the checks are green.
- Behind the default branch, it rebases in the worktree, pushes and keeps waiting in the same
  run, with uncommitted changes set aside and put back. On a rebase conflict it stops and names
  the files: `git rebase origin/<default>` there, resolve, then `kit merge <branch>` again.
- It refuses a failed check, a draft, a closed PR, origin having commits the worktree lacks, and a
  release train holding a PR it would put behind.
- After merging it fast-forwards the default branch wherever it is checked out and removes the
  finished worktree and its branch. A `kept …` line names what stopped that (untracked files, a
  lock, a program in the folder): fix it, then `kit merge <branch>` again — on a merged PR it
  only cleans up. Run from inside the worktree it detaches it and prints the commands that
  delete it.
- With `KIT_HUB_URL` set, the hub merges and deploys: `kit merge` returns after the push with the
  pipeline and `kit hub follow <id>`; once the hub merged, `kit merge <branch>` again cleans up, or
  `--follow` waits, cleans up and exits with the outcome (run it in the background). A hub refusal
  prints its fix; a hub that does not answer only warns, and kit merges locally. A release PR is
  merged and tagged locally, only its deploy going to the hub (no Coolify credentials needed here).
- Where the manifest's `deploy` sets `"auto": true`, the merge is a production deploy (its question
  says so), which an agent harness may refuse whatever the user approved: get the PR green, hand
  the user `kit merge <branch> --yes`, and plan nothing that waits on it: branch follow-ups from it.
- Run every `left for you:` line it prints.
- When the PR moved a lockfile or the kit pin, run `kit sync` in the checkout it fast-forwarded.

## Refused everywhere

`git push`, `git tag <name>`, `npm publish`, `gh pr merge` and `gh workflow run`: the guard, the
hooks or GitHub refuse them. Releases are `kit release`, tags come from `kit merge`, publishing
is CI's. Do not look for a way around them.

## Delegate by default

Where the harness has subagents:

- Explore with read-only explore subagents, so their file dumps stay out of your context.
- Implement with worker subagents, one lane per independent set of files, each in its own
  worktree. Workers commit locally and never push. Use the model the user or the harness sets;
  do not pick one.
- Make each lane's worktree with `git worktree add -b <branch> <dir> origin/<default>` and run
  `kit sync` in it before the lane starts — one worktree at a time, not all at once: installs
  load the machine too.
- The main session integrates the lanes, runs the gates once and pushes through `kit push`.
  Never run the full gate in every lane at once: the lanes share one machine.
- An isolated agent worktree can leave the shared `core.hooksPath` as an absolute path;
  `kit push`, `kit merge` and `kit sync` reset it to `.githooks` and say so. Nothing to undo.
- A lane's worktree goes when `kit merge <branch>` merges it. Remove an abandoned one by
  deleting its folder (Node's `fs.rmSync`), then `git worktree prune` — never
  `git worktree remove`: on Windows it follows the junctions npm makes and deletes what they
  point at.
