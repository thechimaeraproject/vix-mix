# Report a kit issue

When the kit misbehaves, or you make a mistake a clearer kit doc would have prevented, file it on
the kit's GitHub issues at once, tell the user, and carry on with the task. The kit's docs improve
only by what their readers report.

## When

- A `kit` command, a hook, the guard, a doctor row, a generated file or a kit package does
  something wrong or surprising: the wrong target, a refusal that does not say what to change, a
  fix that does not fix.
- A kit doc — the handbook, a `kit-*` skill, the `CLAUDE.md` block — is wrong, missing or
  misleading.
- You made a mistake a clearer doc, a better error message or a refusal would have prevented,
  even if you already undid it. The undo goes in the report; it is no reason to skip it.
- Report as soon as you find it, while the command and its output are in front of you — not at
  the end of the task.
- Not for a bug in the repository's own code, or a question only the user can answer.

## Search first

```bash
gh issue list --repo thechimaeraproject/chimaeraproject-kit --state all --search "<words>"
```

- Search with the command's name and words from its output. A closed match means the fix
  regressed or has not reached this repository's tooling: say which.
- When one matches, add what you saw to it instead of filing a duplicate:
  `gh issue comment <n> --repo thechimaeraproject/chimaeraproject-kit --body-file <file>`.

## Write the body to a file

Write it with your file tool, never inline: a body is multi-line, holds backticks and `$` the
shell would expand, and may quote a command the guard refuses. Five sections:

- **What happened:** the command you ran and its exact output.
- **What was expected.**
- **Where:** the repository and branch, the tooling version (`kit --version`, run in that
  repository), the OS and the agent harness.
- **How it was recovered:** what you did to put things back, or that nothing needed it.
- **What would have prevented it:** the doc, error message, refusal or doctor check, and where
  it belongs.

No secrets, tokens, or environment values that carry credentials. Write paths relative to the
home directory (`~/…`).

## File it

```bash
gh issue create --repo thechimaeraproject/chimaeraproject-kit --title "<the defect, stated>" --label bug --body-file <file>
```

- The title states the defect as a fact: "kit link installs into $VIRTUAL_ENV instead of the
  checkout's .venv", not "problem with kit link".
- `--label bug` when the kit did something wrong, `--label documentation` when a doc was
  missing or misleading, both when both. Those two exist; do not create labels.

## Then

- Give the user the issue URL `gh` printed, in your reply.
- Carry on with the task. Fixing the kit is not part of it unless the user says so.
- No `gh`, or `gh auth status` says you are not logged in: put the whole issue — title, labels
  and body — in your reply for the user to file.
